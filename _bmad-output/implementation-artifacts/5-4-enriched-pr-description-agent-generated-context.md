# Story 5.4: Enriched PR Description with Agent-Generated Context

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a developer reviewing PRs created by bmad-bot,
I want the PR description to include meaningful context, testing instructions, and additional information generated by the agent,
So that I can review the PR efficiently without having to reconstruct what was done and why.

## Acceptance Criteria

1. **Given** a development session completes successfully
   **When** the daemon creates a PR
   **Then** the PR description follows this structured template:
   ```
   # 📋 Story: {story_key} — {story_title}
   **Status:** {outcome_summary}

   ## 📝 Context
   > {agent-generated context describing the purpose and what was implemented}

   ## 🤖 Supervisor Decisions
   > {decisions table or "No supervisor decisions were made during this session."}

   ## 🧪 How to test
   > {agent-generated step-by-step testing instructions}

   ## ℹ️ Additional information
   > {agent-generated notes on dependencies, caveats, or concerns}

   ---
   *Generated by [bmad-bot](https://github.com/jbanety/bmad-bot)*
   ```

2. **Given** a development session completes successfully
   **When** the agent reaches the end of the dev-story workflow
   **Then** the agent produces a structured PR summary containing: a context paragraph, testing instructions, and any additional information
   **And** this summary is captured and stored in the `SessionOutcome::Completed` variant

3. **Given** a development session fails
   **When** the daemon creates a failure PR
   **Then** the PR description uses the same enriched template
   **And** the `⚠️ Failure Details` section appears between `📝 Context` and `🤖 Supervisor Decisions`
   **And** the context, how-to-test, and additional-info sections use fallback text (no agent summary is available for failed sessions)

4. **Given** a development session is escalated (needs human clarification)
   **When** the daemon handles the escalation
   **Then** the daemon NOW creates a PR for the escalated story (⚠️ NEW BEHAVIOR — currently the `Escalated` branch does NOT create a PR)
   **And** the PR title uses the failure format: `wip({story_key}): {story_title} [NEEDS REVIEW]`
   **And** the PR description uses the enriched template with:
   - Context: auto-generated from `EscalationReport` fields (question, reason, partial_work_summary)
   - Failure Details: escalation question and reason
   - How to test: "N/A — session was escalated and requires human clarification."
   - Additional information: partial work summary from the escalation report
   **And** partial code is pushed to the branch before PR creation (same pattern as the existing `Failed` branch)
   **And** the story is still marked `needs-clarification` in sprint-status.yaml (existing behavior preserved)

5. **Given** the agent does not produce a PR summary (crash, timeout, context limit)
   **When** the daemon builds the PR description
   **Then** fallback text is used for each section:
   - Context: "Development session completed. No detailed context was captured."
   - How to test: "Run `cargo test` to verify all tests pass. Review the changed files for correctness."
   - Additional information: "No additional information available."
   **And** the PR description is never empty or malformed

6. **Given** the existing unit tests for `build_pr_description`
   **When** this story is complete
   **Then** all existing tests are updated to match the new template format
   **And** new tests cover: enriched description with all fields populated, fallback behavior when fields are `None`, failure PR with fallback, escalation PR with auto-generated context from EscalationReport

### Module Dependency Design — PrSummary vs Raw Strings

**Problem:** `PrSummary` is defined in `src/git_provider/mod.rs`. Adding it directly to `SessionOutcome` (in `src/session/mod.rs`) would create a `session` → `git_provider` dependency that doesn't exist today.

**Solution:** Store raw `Option<String>` fields in `SessionOutcome::Completed`. The pipeline (which already imports both `session` and `git_provider`) constructs `PrSummary` from these raw strings.

```
SessionOutcome::Completed {
    story_key: String,
    branch: String,
    decisions: Vec<DecisionRecord>,
    pr_context: Option<String>,        // NEW — raw text from agent
    pr_how_to_test: Option<String>,    // NEW — raw text from agent
    pr_additional_info: Option<String>, // NEW — raw text from agent
}
```

In `pipeline.rs`:
```rust
let pr_summary = pr_context.map(|ctx| PrSummary {
    context: ctx,
    how_to_test: pr_how_to_test.unwrap_or_default(),
    additional_info: pr_additional_info.unwrap_or_default(),
});
```

### PR Summary Extraction Format

The agent should produce the PR summary using XML-style tags for reliable parsing:

```xml
<pr-summary>
<context>
Implemented the integration test infrastructure including shared test fixtures,
mock providers, and helper utilities. This provides the foundation for all
subsequent integration test stories (7-2 through 7-10).
</context>
<how-to-test>
1. Run `cargo test --test integration` to execute all integration tests
2. Verify fixture files are created in the temp directory
3. Check that mock providers return expected responses
</how-to-test>
<additional-info>
- Added `tempfile` as a dev dependency for test directory management
- Mock LLM provider reuses patterns from unit tests in src/session/mod.rs
- Test fixtures are self-cleaning via Drop implementation
</additional-info>
</pr-summary>
```

XML tags are preferred over markdown headers because:
- No ambiguity with the agent's regular markdown output
- Reliable regex extraction with `<tag>(.*?)</tag>` (dotall mode)
- The agent already works with XML context activation (BMAD persona format)

### Pipeline Data Flow

```
Agent Session (Completed)
  └─ post-commit prompt: "Commit ALL uncommitted changes..." (existing)
  └─ post-summary prompt: "Provide a PR summary..." (NEW)
      └─ parse_pr_summary() extracts (context, how_to_test, additional_info)
          └─ stored in SessionOutcome::Completed { pr_context, pr_how_to_test, pr_additional_info }
              └─ pipeline.rs constructs PrSummary from raw strings
                  └─ PrDescriptionParams { pr_summary: Some(summary), ... }
                      └─ build_pr_description() renders enriched template
                          └─ GitHub/GitLab PR created with rich description

Agent Session (Escalated — NEW PR creation)
  └─ EscalationReport { question, reason, partial_work_summary }
      └─ pipeline.rs constructs PrSummary from report fields (no agent prompt needed)
          └─ PrDescriptionParams { pr_summary: Some(summary), failure_details: Some(...) }
              └─ build_pr_description() renders enriched template
                  └─ GitHub/GitLab PR created with escalation context

Agent Session (Failed)
  └─ No agent summary available (session crashed)
      └─ PrDescriptionParams { pr_summary: None, failure_details: Some(error) }
          └─ build_pr_description() uses fallback constants for context/test/info sections
```

### Fallback Chain

```
Session Completed:
  Agent produces <pr-summary>?
    ├─ Yes → parse_pr_summary() succeeds?
    │    ├─ Yes → PrSummary used directly
    │    └─ No  → log warning, pr_summary = None → fallback constants used
    └─ No (prompt failed) → pr_summary = None → fallback constants used

Session Escalated:
  PrSummary auto-generated from EscalationReport fields (always available)

Session Failed:
  pr_summary = None → fallback constants used (agent unavailable)
```

### Anti-Patterns to Avoid

- **Don't make the PR summary prompt blocking** — if the agent doesn't respond or produces garbage, the session should still complete successfully with `None` fields
- **Don't parse the agent's entire conversation history** — only parse the response to the explicit PR summary prompt
- **Don't put the PR summary instructions in the system prompt** — put them in the preamble's tool usage section as a post-completion instruction
- **Don't import `PrSummary` into `session/mod.rs`** — use raw `Option<String>` fields in `SessionOutcome` to avoid cross-module coupling; construct `PrSummary` in the pipeline
- **Don't add PR summary fields to `SessionOutcome::Failed`** — the agent is unavailable after a crash, so these fields would always be `None`
- **Don't insert the PR summary prompt BEFORE the commit prompt** — commits must happen first so the PR reflects the final committed state

### Scope Boundaries

**In scope:**
- New `PrSummary` struct and enriched PR description template
- Agent preamble instructions for producing PR summary
- Extraction/parsing of PR summary from agent response (post-commit)
- Fallback handling when summary is unavailable
- **NEW: PR creation for escalated sessions** (pipeline behavior change)
- All test updates

**Out of scope:**
- Changing how review reports are posted (they remain as PR comments via `add_comment()`)
- Modifying the notification format (Telegram messages — separate concern)
- Adding PR labels or assignees
- Changing the PR title format (`build_pr_title()` is unchanged)
- Making escalation PRs auto-merge or change status (they remain `needs-clarification`)

### Testing Requirements

- All existing `build_pr_description` tests must be updated to pass with the new template
- New tests for enriched content, fallback behavior, and parser edge cases
- `parse_pr_summary()` must handle: valid XML, partial XML, no XML, nested tags, special characters in content
- Pipeline tests (if any exist) should verify `pr_summary` flows through correctly
- Escalation PR creation should be testable via the existing `build_pr_description` unit tests (the PR builder is provider-agnostic)
